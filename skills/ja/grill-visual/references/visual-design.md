# 議論のためのビジュアル設計

読む人が「選ぶと、自分の作業がどう変わるか」を図で確かめられるページにする。
文章の箱を増やす前に、対象の形と見せる差を決める。
答え方（回答欄・回答バー）は毎回同じにし、図は毎回その論点のために発想する。
見た目の既定・色の決め方・図の型と描き方・物差しは 土台（`assets/foundation/`）の 01〜05 に従う。この文書は、議論ページに固有の見せ方を書く。

## 0. 同じものを量産しない

- 質問ごとに、表現の候補を2〜3個考えてから、その論点の差が最もよく見えるものを選ぶ。
- 例の図（`assets/fig.example.svg`）と過去の議論ページの図を写さない。回答欄・回答バー・Before→After の枠は組み立て（`scripts/build.mjs`）が差し込むので、書かない・写さない。
- 同じラウンドで同じ型の図（箱と矢印だけ、など）を並べない。前のラウンドと同じ見せ方が最善なら、その理由がある場合だけ使う。
- 下の表と表現の一覧は出発点の例。ここにない表現（地図、断面図、漫画のコマ、天秤、温度計、時計、部屋の見取り図など）も、論点に合えば使う。

## 1. 論点を、見える差に置き換える

| 決めたいこと | 主に見せる差 | 表現の例 |
| --- | --- | --- |
| 通知や処理をまとめるか | 数・まとまり・届くタイミング | 同じ3件が1つの通知になる図と、3通知に分かれる図 |
| 何から取り組むか | 順位・位置 | 同じ仕事を保持したまま順番が動く小さな一覧 |
| どこに残すか | 場所・表示範囲 | 一覧と履歴の領域、未完了／完了の切り替え |
| 誰に渡すか | 主体・接続・引き継ぎ | 担当者ごとのレーンと受け渡しの矢印 |
| いつ行うか | 順序・待ち時間 | 時間軸上のイベントと待つ区間 |
| 費用や容量の違い | 同じ尺度での量 | 根拠のある値を共通スケールで比較する棒 |

### 標準の表現（例であり、ここに限らない）

| 表現 | 向いている問い | 描き方の要点 |
| --- | --- | --- |
| 場面のイラスト | 選んだ後に人が何をするか | 人物・道具・画面を1コマに置き、吹き出しや矢印で行動を示す |
| 実物そっくりのUIモック | 画面・通知・一覧の見え方 | 実際に見る画面の部品（ボタン、通知、行）を簡略化して描く |
| たとえ話の絵 | 仕組みが抽象的で掴みにくい | 身近な物に置き換え、実際の動作との対応を短く添える |
| 数量のチャート | 件数・時間・費用の差 | 根拠のある値だけを同じ尺度で並べる |
| ステップ再生 | 順序・受け渡し・状態の変化 | 3〜5コマ。▶で1コマずつ、「再生」を押したときだけ自動送り |

同じ入力・同じ尺度で比較する。変更した条件と変化した箇所を短く添える。
仮の例や件数はそう表示し、架空の数値を実測値や効果の予測に見せない。
複数の関係を一枚に詰めず、概要図から各論点の図へ移動させる。

### 図の注文書を書いてから描く

問いごとに、選んだ表現を注文書（page.json の `order`）に2行までで書き出してから描く。
形と例は [data.md](data.md) の「図の注文書」。候補を2〜3個考えるのはメインで、注文書には選んだ1つだけを書く。
同じラウンドの注文書を並べて、「表現」が同じ型ばかりになっていないかを見る。

## 2. 図の構造と見た目を整える

- 要素は対象を描く。仕事なら行、通知なら通知パネル、保存先なら領域という形を使い分ける。
- 矢印は「何がどちらへ進むか」を説明する。装飾や意味のない全結合を避ける。
  接続先と線の端を一致させ、線を文字・他の要素の上に通さない。
- 重要な差は位置・大きさ・数で見せ、色とアイコンは理解を補う。
  色の意味を揃え、状態は文字でも示す。主な強調色は1色、状態用は少数に絞る。
- 全体図を最初の画面に置き、図・短い説明・選択肢の順で視線を導く。
  図が主役になる面積を確保する。すべてを同じカードの反復にしない。
- 見出し、本文、注記に段階を付ける。日本語本文は読みやすい行間と行幅にし、
  長文は折りたたむ。利点・不便・推奨理由は開かなくても読めるようにする。
- イラストはSVGの図形で描く。人物は頭と胴の簡単な形で十分。表情や細部より、位置・向き・持ち物で意味を伝える。
- PCの表示領域を基本に、図と選択肢を無理なく読める配置にする。
  モバイル対応も依頼された場合は図と選択肢を縦に並べ、文字を縮めすぎない。

## 2.5 決定の Before→After を描く

- 文字を箱に入れて矢印でつなぐだけにしない。前と後で変わる物そのもの（数、並び、画面、人の動き、壁や出口）を描く。
- 前と後は同じ描き方・同じ尺度にし、違う箇所だけが目に入るようにする。
- 前の背景は灰色、後の背景は決定色など、どちらが今後かを色と「前」「後」の文字で示す。
- 図の下に、前と後をそれぞれ1行で書く。

## 2.6 案で変わる図は、下絵1回と層で描く

案を切り替える図は、案ごとに全部を描かない。どの案でも同じ所（下絵）を1回だけ描き、案で変わる所だけを層（`<g data-layer="A">`）にする。
字数や部品の数に上限は置かない。表現の幅を狭めずに、重なりだけを減らすため。

- 描く前に「どこが変わるか」を決める。注文書の「層」に書いた物だけを層に入れる。
- 下絵は同じ例・同じ尺度で描き、層は下絵の上に重ねる。案ごとに尺度や配置を変えない（比べられなくなる）。
- 決定の Before→After は、同じ断片の別の層を指す（`before: {layers: ["N"]}`）。前の姿が選択肢に無ければ、`N`（今）などの層を足す。
- 複数選択の問いは選んだ案の層が重なって出るので、重ねても崩れない形に描く。
- ステップ再生のコマも同じ考え方で、`data-frame`（そのコマだけ）か `data-step`（そのコマから）で重ねる。
- 例は [../assets/fig.example.svg](../assets/fig.example.svg)。決まりは [data.md](data.md) の「図の断片」。

## 3. 操作に、比較する意味を持たせる

案を選ぶと同じ例の表示が変わるようにする。タブの色だけを変えたり、説明を交換するだけで済ませない。
並び替え・絞り込み・処理の順序など、問いの理解が深まる操作だけを用意する。

- 推奨の表示（「A案を表示・未選択」）・案の切り替え・ステップ再生のボタンとコマの表示・`fieldset/legend`・回答欄は、組み立てが付ける。メインは、その中で変わる絵（層とコマ）を描く。
- 回答は空で始める。
- 選択は未送信のメモ。確定した決定数には加えない。保留も選べるようにする。
- 移動を追いやすくする短いアニメーション（目安150〜260ms）は使ってよい。
- ステップ再生は、前へ・次へ・再生／停止のボタンと、何コマ目かの表示を付ける。
  開いただけで動き続けるループ、スクロール連動、点滅は使わない。`prefers-reduced-motion` でも手動送りは使える。
  キーボード操作では即時更新を優先し、`prefers-reduced-motion` では動きを止める。
- ラジオ・ボタン・`details` 等の標準要素、ラベル、見えるフォーカスを使う。
  グループを `fieldset/legend` で説明し、図には代替説明を付ける。
- 回答欄と回答バーは組み立てが `assets/frame/` から差し込む。形と動きを変えない。
  コピーなどの操作結果は `role="status"` で伝え、成功表示と実処理を一致させてある。
- JavaScriptが使えなくても基本図と案の説明を読めるようにする。
  保存や送信の有無、再読み込みで消える情報はユーザーに分かる場所へ置く。

## 4. HTML・CSS・JavaScript は組み立てが受け持つ

- ページの CSS・JavaScript（土台の tokens.css・parts.js、回答欄と回答バー、案の切り替え、ステップ再生のボタン、層とコマの表示）は、`build.mjs` が `assets/frame/` と土台から差し込む。モデルは CSS・`<script>` を書かない。
- 図の断片は SVG と土台の変数だけで書く。部品を使いたいときは `.js` の断片で parts.js を呼ぶ（[data.md](data.md) の「図の断片」）。
- 組み立てたページは標準の CSS・SVG・JavaScript だけで、実行時の通信は要らない。Tailwind CSS・daisyUI・CDN は足さない。アイコンが要るときは断片の中に SVG で描く（Lucide などを写すときはライセンスを残す）。

## ブラウザで確かめる範囲

ブラウザではPCの代表的な1画面で、図の接続・選択肢の表示・メモへの反映を実際に確かめる。
確認は変更に関係する範囲に絞り、スマートフォン向けの設計・検証は明示要件がある場合だけ行う。
