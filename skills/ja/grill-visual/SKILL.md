# 図を見ながら、計画を詰める

1問ずつ背景・争点・選択肢・推奨をそろえて聞く質問の設計に、大きな図と平易な説明を組み合わせる。
初めて読む人が「何を決めるか」「選ぶと何が変わるか」を理解できるHTMLを先に作り、
そのページを共通の資料として議論する。必要な手順はこのスキルに含む。

ページは組み立てで作る。モデルが書くのは、問いと決定のデータ（`page.json`）と図の断片（`fig/`）だけ。
土台の tokens.css・骨格の CSS と JS・回答欄・回答バーは `scripts/build.mjs` が差し込む。図はメインが問いごとに描く。

## 呼び出し

`$grill-visual [対象の計画・資料・論点] [q=N] [r=N]`

- 対象の省略時は会話中の計画を使う。対象を特定できなければ、その情報だけ聞く。
- 既定では質問数・ラウンド数に上限を置かない。ユーザーの「終わり」、または未決ゼロで終了する。
- `q`（質問総数）・`r`（ラウンド数）を指定したときだけ上限として扱う。
  0が指定されたら質問せず、論点と推奨を資料にまとめる。
- 既存の議論を再開するときは、page.json と discussion.md から質問数・回答・未決事項を引き継ぐ。

## 質問する前に

対象のコード・資料・関連する記録を読み、現状、目的、決定済み、未確認を分ける。
調べれば分かることは調べる。既に決まったことは、新しい矛盾や条件変更がない限り聞き直さない。
質問はユーザーの意図、優先順位、範囲、許容する不便に絞る。

まず論点を影響度順に並べ、安定したIDを付ける。
各論点に背景、影響度、後戻りのしやすさ、依存するIDを付ける。
公開範囲・削除・データ形式・外部依存など、後から変える費用や影響が大きいものを上位に置く。
未決事項がなければ、質問を水増しせず決定の要約を作る。

## 置き場と、読む物

保存先は、呼び出しで指定されたフォルダ、プロジェクトの成果物ルール、作業ディレクトリの `artifacts/grill-visual/<topic>/` の順に決める。
リポジトリに残したくなければ、そのフォルダを `.gitignore` に入れるよう持ち主に伝える。
別の議論があれば上書きせずディレクトリを分ける。同じ議論ではURL・IDを維持して更新する。

```
artifacts/grill-visual/<topic>/
├── page.json       問い・決定・経緯（モデルが書く）
├── fig/qNN.svg     問いごとの図の断片（メインが書く。数の図は .json、場面の図は .js も可）
├── discussion.md   記録（モデルが書く）
├── index.html      組み立てた議論ページ（build.mjs が書く。手で直さない）
├── summary.html    組み立てたまとめ（同上）
└── tasks.json      終わったら。タスクの正（モデルが書き、エージェントが scripts/task.mjs で書き戻す。tasks.js は build.mjs が書く）
```

- 初回だけ、土台の地図と 01（好み・原則）・02（見た目の方向）を読む。土台はスキルの中の `assets/foundation/`（README.md が地図）にあり、無ければ隣の `html-foundation` スキル（SKILL.md が地図）を使う。方向は題材から選び、page.json の `direction` に書く（迷えば `blueprint`）。
- 初回だけ、[references/data.md](references/data.md)（page.json・図の断片・注文書・tasks.json の形）と [references/visual-design.md](references/visual-design.md)（議論ページの見せ方）を読む。
- 骨格の CSS・JS・ひな形（`assets/frame/`）は読まない。組み立てが差し込み、形を守る。
- 例: [assets/page.example.json](assets/page.example.json)（架空の議論「ToDo アプリに通知を付ける」の6問・6決定）、[assets/fig.example.svg](assets/fig.example.svg)（SVG で描く例。下絵1回・3案の層）、[assets/fig.example.js](assets/fig.example.js)（部品で描く例）、[assets/tasks.example.json](assets/tasks.example.json)。

## ページの中身

組み立てが、page.json から次の順に並べる。モデルは各項目のデータと図を用意する。

1. **何を決めるページか。** 目的を1文（`title`）、このラウンドで決めること（`lead`）。版・ラウンド・質問済み数・決定数は組み立てが出す。
   `q`/`r` を指定したときだけ `limits` に書き、「（上限12）」が添えられる。
2. **論点の依存マップ。** どの論点が決定済み・今回・後でかを示す。図は描かない。組み立てが、page.json の `map.nodes`（ID と短い名前）と問いの `after` から札と線を描き、状態を色と文字で塗り、札から各質問へ移動できるようにする。
   対象の仕組みの絵は、初回の区画（`intro`）の図に置く。診断などの区画は `intro` に置く。区画の図は1ラウンド1枚までにする（図の枚数が出力と時間にそのまま効くため）。
3. **今回の質問。** 既定6問・最大8問。前提の回答待ちの論点は後に回す。独立した問いが少なければ減らす。ここには回答待ちの問いだけが全文で並ぶ。
4. **全体の備考。**
5. **決まった問い・見送り。** 組み立てが1件ずつ畳み、題と「決定（A）」「見送り」の札だけを見せる。今回答える問いと紛れさせないため。開くと元の図・選択肢があり、札や決定のリンクから飛ぶと開く。
6. **決定の Before→After。** 決定ごとに、前と後で変わる物そのものを絵で並べる（`decisions[].before/after` が同じ断片の別の層を指す）。
   理由・引き受けた不便・却下した案は畳む。
7. **常時表示の回答バー。** 画面下に固定する。今回の問いのうち、まだ選んでいない問いの ID をリンクで出す。

### 分かりやすさと判断材料を両立する

- 全質問に、その問いの中身を説明する図を置く。図では主体・矢印の意味・結果を明記し、飾りだけの図にしない。
- 場面のイラスト、実物そっくりのUIモック、たとえ話の絵を標準の表現にする。
  数値に根拠があればチャートも使う。これらは例であり、ここに挙げたものに限らない。
- 順序や移動を追う問いはステップ再生にする（断片の `data-frame`・`data-step` と問いの `steps`）。▶で1コマずつ進め、「再生」を押したときだけ自動で送る。
- 選択による変化が判断を助ける場合は、案の切り替えで同じ例の表示を変える。**下絵は1回だけ描き、案で変わる所だけを層（`<g data-layer>`）にする。** 案を見るボタンと選択で層が替わる。
- 身近な言葉や具体例を使う。たとえ話は補助にし、実際の動作や重要な条件も書く。
- 背景の詳細・技術的な根拠は `details` に置く。
  選択で生じる主な不便・費用・リスクと推奨理由は、開かなくても読める場所に残す（`pros` `cons` `why`）。
- 「確認した事実」「提案」「未確認」と「決定済み」「回答待ち」を混同しない。
  状態は色だけでなく文字で示す。推奨案を選択済みや決定済みの見た目にしない。
- PCで読む資料を基本にする。スマートフォン向けの設計・検証は明示的な要件がある場合だけ行う。

### 1問の中身

各質問は page.json の `questions` に1件ずつ書く（項目は data.md）。安定したIDとページ内アンカーは組み立てが付ける。

- **背景（`background`）：** 分かっている現状と具体例。事実の根拠と仮定を区別する。
- **争点（`issue`）：** 未決のことと、その回答で変わる操作・表示・運用。
- **図（`fig`）と注文書（`order`）：** 論点ごとに発想した図。見せる差・表現・主役・層を注文書に2行までで書いてから描く。
- **選択肢（`options`）：** A/B/Cなど、違いを比較できる案。各案の利点と引き受ける不便を書く。複数を選べる問いは `multi`。
- **推奨（`recommended` `why`）：** 現在の目的に合う案と、そう判断する理由。前提が変われば推奨も見直す。
- **備考欄と「保留にする」ボタン**は組み立てが付ける。

依存する質問は前提の回答を受けてから出す。
不合格の例：結論と質問だけの簡素な出力。背景が1行しかない質問。根拠のない推奨。

### 回答の形（固定）

回答欄（ラジオかチェックボックス・保留・備考）と回答バーは、組み立てが `assets/frame/` から差し込む。形と動きを変えない。

- 回答バーは選択・備考を `Q01: A（名前）` と `  備考: …` の行にまとめて `#answer-text` に出す。空欄の備考は出さない。
- 「回答をコピー」は押した1回でクリップボードへ送る。Claude の内蔵ブラウザ（ローカルのファイルを `data:` の写しで開くので、clipboard API が無い）でも、file:// で直に開いても同じにする。
  成功表示は実際の成功後に出し、どの方法でも写せなかったときだけ文を選択して手動コピーを案内する。
- 回答メモは未送信の下書き。決定数に加えない。再読み込みで消えることをバーに書いてある。

## 1ラウンドの手順

初回も回答後も同じ手順で進める。ページ全体は書き直さず、変わった部品だけを書く。

1. **回答を読む。** 貼られた回答・チャットの回答を使う。ページを読める内蔵ブラウザがあれば、`#answer-text` を直に読んでもよい。
2. **記録とデータを直す。** `discussion.md` に回答と意味を記録し、page.json の変わった所だけを直す（版・ラウンド・`decisions` への決定・次の問い・`rounds`）。新しい問いには注文書（`order`）を書く。
3. **図を描く。** 新しい問いと、描き直す図を（依存マップは描かない。論点が増えたら `map.nodes` に足す）、メインが `fig/` に書く。新しい図は1つのメッセージに Write を並べて全部書く（呼び出しのたびに会話全体を読み直すので、回数がそのまま費用と時間になるため）。描き方の決まりと断片の形は [references/figure.md](references/figure.md)。変わらない図は描き直さない。
   図はサブエージェントに渡さない。担い手は1人ずつ資料とスクリプトを読み直すので、図1枚あたりの出力と費用がメインの数倍になったため。
4. **組み立てる。** `node <このスキル>/scripts/build.mjs <議論のフォルダ> && node <このスキル>/scripts/verify.mjs <議論のフォルダ>/index.html` を1つのコマンドで流す（手順5の確かめまで1回の呼び出しで済ませる）。崩れた page.json や無い図は、項目の場所を示して止まるので直す。
5. **確かめる。** verify は物差しを全案・全コマ・ダークで回し、回答欄を押して読み、clipboard API を消したページで「回答をコピー」を1回押して写せるかを見て、スクショを1枚撮る。
   ✗ があれば、その図か page.json をメインが Edit で直し、4から流す。page.json と図は Read で読み返さない（会話に入った分だけ、後の呼び出しが重くなるため）。スクショは Read で見る。
6. **渡す。** ページを開いて持ち主の前に出し、リンクと今回の争点・回答方法を短く伝える。開いたページの文字は読み込まない（`get_page_text`・`read_page` を使わない。見た目は verify のスクショで見る）。チャットではHTMLの全文を繰り返さない。
   - Claude のデスクトップアプリでは、次の順に開く。ローカルのファイルは開いた時点の写しで表示され、同じ URL を開き直しても再読み込みしても新しい版にならないため。
     1. `tabs_context` に同じファイルのタブがあれば `tabs_close` で閉じる。閉じるとそのタブの回答メモも消えるので、手順1で読み終えてから閉じる。
     2. `preview_start` に `file://<絶対パス>` を渡して開く。
     3. `show_pane`（`pane: "preview"`）でブラウザのペインを前に出す。隠れたままだと、開いても持ち主に見えない。「どの窓にも開いていない」と返ったら、ブラウザのペインで開いたこととファイルのパスを伝える。
   - ページは作業フォルダの下に置く。`/tmp` の下に置いたページは、内蔵ブラウザで開いても道具から読めなかった。
   - ほかの環境では、その環境の内蔵ブラウザで開く。内蔵ブラウザが無ければ、既定のブラウザで開く（macOS は `open`、Linux は `xdg-open`）。

回答方法は次の3つを案内する。

1. ページで選び、回答バーの「回答をコピー」で貼り付ける（基本）。
2. チャットに `Q01:A、Q02:C`、自由文、保留を直接書く。
3. ページを読める内蔵ブラウザがある環境では、ページで選んでチャットに「回答した」とだけ送ってもよい。エージェントが `#answer-text` を読む。読めなければ1を頼む。

選択肢を出す質問ツールがあれば、今回の問いが4問以下でツールの上限に収まるときだけ併用してよい。
ダイアログが閉じられたら、ページでの回答を待つ。

論点をユーザーが指定していれば、その範囲から始める。範囲も任されていれば影響の大きい論点を選ぶ。

### 回答を受けたら

- 決まった問いは `decisions` に足す。札「決定（A）」は組み立てが付ける。前と後の図は、その問いの断片の層を `before` `after` で指す。前の姿の層が無ければ、メインがその断片に層を足す。
- 一部回答は受けた分だけ確定し、残りを未回答として残す。説明の依頼には同じIDの説明を補い、新しい質問として数えない。
- 「保留」と備考が食い違うなど、回答の解釈が結論に影響する場合は、採った解釈を `rounds[].notes` と discussion.md に明記し、違えば直すよう伝える。

各バッチへの回答後に、未決・保留と、その回答や備考で新たに具体化した論点を見直す。
ユーザーの判断が必要な論点が残れば、同じページに次のバッチを作って続ける。
備考に要望が書かれていたら、それを新しい論点にするか、決定に反映するかを判断する。
現在の質問に回答が揃っただけでは、議論全体の終了としない。
追加の判断が不要なら、その理由と残る仮定を示して終了する（`status: "ended"` と `end`）。回数を埋めるための質問はしない。

## 上限と記録

`q`/`r` を指定した場合だけ、`q` は出した意思決定の問いの数、`r` はそのバッチ数として記録する。
1バッチの中で複数事項の採否を求める場合も、それぞれを問いとして数える。
上限に達したら追加の掘り下げを止め、残った論点を影響度・推奨・見直す条件付きの仮定一覧にまとめ、
「推奨案で進める仮定」としてまとめて1回だけ承認を求める。この締めの確認は通常の質問枠とは別に記録する。
採用されていない事項は保留として残す。未回答を承認とみなさない。
上限を指定していないときも、使用した質問数・ラウンド数は記録する。

`discussion.md` は議論の記録とし、page.json と同じ版番号を付ける。
開始時から作り、少なくとも以下を保存する。

- 目的、対象資料、決定済みの前提、論点と依存関係、使用した質問数・ラウンド数（指定時は上限も）。
- 質問ID、質問本文、提示した選択肢と推奨、回答、備考、採用内容、理由。
- 仮定・未確認事項とその影響、却下した代替案と理由、再検討する条件。
- 次に見る質問IDまたは議論終了の理由。決定が0件なら「まだ決定なし」と書く。

計画本体がある場合は合意した決定を反映し、記録から参照する。
議論しただけで実装済みと扱わず、実装などの作業範囲は会話で任されている範囲に従う。

## 終わったら、まとめを作る

議論が終わり（未決ゼロ・「終わり」・上限到達）、決定が1件以上あれば、聞かずに同じフォルダへ `summary.html` を作る。
決定が0件なら作らない。まとめも組み立てで作る：page.json に `summary`（文・完成形と仕組みの図の断片・仮定・見直す条件）を足し、タスクを `tasks.json` に書いて、`build.mjs` を流す。
章の枠・決定のカード・タスクの章・経緯の図は組み立てが作る。手順は [references/summary.md](references/summary.md)。

まとめの後にタスクを進めるときは、tasks.json の `for_agent` に従う。
- tasks.json は手で書かず、`node <このスキル>/scripts/task.mjs <議論のフォルダ>` で書く（ロックを取るので、2つの書き手が同時に書いても壊れない）。取るときは `doing --by 担当` で、担当が `run_by` に入る。
- いま取れるタスクは、番号の小さい順に親が1件ずつ進める。サブエージェントには、持ち主が明示したときだけ渡す。
- 渡すときは files が重ならないタスク（まとめの4章の「並べて動かせる」）だけにする。サブエージェントが書くのは自分のタスクの doing と step だけで、done は親が `how_to_check` で確かめてから書く。形と操作の一覧は [references/data.md](references/data.md) の「書き方」「並べて進める」。

## 完了前に確かめる

- verify.mjs が ✗0 か。! は html-check を流して中身を見て、直すか決める。
- 依存マップから質問へ移動でき、各質問に中身を説明する図があり、選択肢の違いと推奨理由が分かるか（スクショと、渡すときに開いた1画面で見る）。
- 図が見本や前のラウンドの写しになっていないか。同じラウンドで同じ型の図ばかり並んでいないか（注文書の「表現」を見比べる）。
- 説明に使う件数・並び・接続と、実際の図の表示が一致しているか（verify は文と図の一致を見ないので、スクショと渡すときの1画面で見る）。
- page.json・discussion.md・ページの版・ID・決定・未回答が一致しているか。
- 渡す前に、確かめのために選んだ回答は残っていない（verify は自分のブラウザで押し、渡すページには残さない）。内蔵ブラウザで開いて押した物は再読み込みで消す。
- ブラウザが使えなければ verify の結果とスクショで伝え、実画面は未確認と伝える。
- HTMLのリンク、反映した決定、残った論点、次に答える場所を簡潔に伝える。
  資料作成だけを頼まれた場合は、実際の質問を開始せずその成果までで終える。
